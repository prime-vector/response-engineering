## Two measurements, and they answer different questions

`precedent_hit_rate@k` ranks **documents** with nothing truncating: which prior records does the surface order highest. `precedent_hit_rate@limit` counts what survives inside a **fixed passage budget**, where chunk size decides how many distinct documents fit. The first is a property of the ranking, the second of the ranking and the chunker together. How two chunkers differ on either, and at which k, is measured in `chunker-comparison.md` beside this file, which scores both indexes on both. A single-index run cannot see any of that, so this table does not claim it: the budget figure below is this index alone.

The budget is an eval parameter. Nothing binds the agent to it: the surface defaults to 5 passages, `.agents/precedent-analyst.yaml` tells the agent to ask for breadth without naming a number, and no demo passes one. So this is the surface measured under a fixed budget, which is a real question about the retriever, and it is not an estimate of what the agent is handed. What the agent actually asks for is in the adapter's audit log, and judgement mode scores it there as `agent_reach`, because an output reporting its own queries is the agent's account of its own conduct.

**At the run limit of 8 passages: 63.3% (38/60 relevant documents reached).** This is the figure `evals/validate.py` prints as an observation, recorded here so the two are one number rather than two of unstated provenance.

| `agent_reach` | evals/judgement.py: retrieval across the queries the agent chose, which this mode cannot see because it issues one canonical probe per case |
| `cost_per_recall_usd` | unmeasured in either mode: no model runs here, and oa reports no token usage there |

Every one of those is now written and lives in the other mode. They stay listed here because this table would otherwise read as the whole measurement: what the surface hands an agent is not what the agent does with it.

3 limits that judgement mode does not close:

- **Section-level citation is unmeasured, not mitigated.** Ground truth names documents, so nothing here distinguishes a citation of the right document's `Resolution` from its `Gaps`. Adapter-log groundedness would not either: it proves only that a cited passage was in the returned set. See `evals/README.md`.
- **One query per case.** The spec tells the agent to issue several, so a case probing one axis of a multi-axis incident is counted here as missing what its other axis would reach. These numbers are a floor on the surface, not an estimate of the agent. Judgement mode measures the other thing, on the queries the agent chose, and the two are not comparable: nothing truncates a rank there.
- **This table is one index.** Whether a chunker changes retrieval is not visible from it at all, and a sentence here saying so would be regenerated identically whatever the other index did. `chunker-comparison.md` measures that, and CI checks it.

This table is a function of the dataset, the corpus and the config named above, and nothing else. It carries no timestamp and no latency figure for that reason: `python3 evals/runner.py --config evals/config.yaml --check` regenerates it and fails if it has drifted, the same way the fixtures and the corpus index are checked. When a run was recorded, what the surface took, and the per-case detail are in the timestamped JSON beside this file. That latency is the mock over loopback: it measures this repo's fixture retriever, not a vector store.
