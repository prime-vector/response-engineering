## Two measurements, and they answer different questions

`precedent_hit_rate@k` ranks **documents** with nothing truncating: which prior records does the surface order highest. `precedent_hit_rate@limit` counts what survives inside the **passage budget the agent is actually run at**, where chunk size decides how many distinct documents fit. The first is a property of the ranking, the second of the ranking and the chunker together. How two chunkers differ on either, and at which k, is measured in `chunker-comparison.md` beside this file, which scores both indexes on both. A single-index run cannot see any of that, so this table does not claim it: the budget figure below is this index alone.

**At the run limit of 8 passages: 63.3% (38/60 relevant documents reached).** This is the figure `evals/validate.py` prints as an observation, recorded here so the two are one number rather than two of unstated provenance.

## What this run does not measure

| Metric | Why not |
| --- | --- |
| `false_precedent_rate` | judgement mode: one live oa run per case, scored against expect.applicability |
| `no_precedent_accuracy` | judgement mode: 13 no-precedent cases, scored on no_applicable_precedent |
| `false_refusal_rate` | judgement mode: 25 answerable cases, scored on the same field |
| `groundedness` | judgement mode plus a judge prompt at temperature 0, which is not written |
| `divergence_quality` | judgement mode: 7 near-miss cases, scored against expect.divergence_names |
| `cost_per_recall_usd` | judgement mode: no model runs in retrieval mode, so the cost is zero and measures nothing |

3 limits that survive judgement mode being written:

- **Section-level citation is unmeasured, not mitigated.** Ground truth names documents, so nothing here distinguishes a citation of the right document's `Resolution` from its `Gaps`. Adapter-log groundedness would not either: it proves only that a cited passage was in the returned set. See `evals/README.md`.
- **One query per case.** The spec tells the agent to issue several, so a case probing one axis of a multi-axis incident is counted here as missing what its other axis would reach. These numbers are a floor on the surface, not an estimate of the agent.
- **This table is one index.** Whether a chunker changes retrieval is not visible from it at all, and a sentence here saying so would be regenerated identically whatever the other index did. `chunker-comparison.md` measures that, and CI checks it.

This table is a function of the dataset, the corpus and the config named above, and nothing else. It carries no timestamp and no latency figure for that reason: `python3 evals/runner.py --config evals/config.yaml --check` regenerates it and fails if it has drifted, the same way the fixtures and the corpus index are checked. When a run was recorded, what the surface took, and the per-case detail are in the timestamped JSON beside this file. That latency is the mock over loopback: it measures this repo's fixture retriever, not a vector store.
